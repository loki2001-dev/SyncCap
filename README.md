# SyncCap

---

- Modern C++17 multi-channel video and sensor acquisition system, fully simulated without camera hardware
- Captures 3–4 GMSL-style 1920x1080 channels at 20–30 fps with <span style="color:deepskyblue; font-weight:bold">inter-channel frame sync within 2 ms</span>
- libx264 H.264 encoding with timestamp verification before encoding and time-based file segmentation
- Status reporting over HTTP and MQTT, with remote start/stop control through an OpenAPI server
- Real-time Dear ImGui dashboard with a 4-channel live preview of the same capture tick
- Designed as an end-to-end solution: collector, OpenAPI server, MQTT broker and dashboard
- Designed for Docker-based execution (Mosquitto + OpenAPI server, optional collector)
- <span style="color:deepskyblue; font-weight:bold">Requires sample media (`samples/video/*.mp4`, generated by `scripts/make_samples.py`) for file inputs, or use `config/collector.synthetic.json` to run without any input file</span>
- Runs on Windows 10/11 (MSVC x64) and Ubuntu 24.04 or later

## Features
- Input Abstraction: `IVideoSource` with <span style="color:deepskyblue; font-weight:bold">file (MP4/AVI), webcam (OpenCV), network (RTSP/HLS) and synthetic</span> sources, `ISensorSource` with CSV and simulated (`std::mt19937`) sensors
- Asynchronous Capture: one reader thread and one capture thread <span style="color:deepskyblue; font-weight:bold">per channel</span>, 3–4 channels at 20–30 fps
- Frame Synchronization: common software FSYNC tick + <span style="color:deepskyblue; font-weight:bold">absolute-deadline latch</span> + per-set verification; sets over 2 ms are dropped and logged, so every channel keeps the same frame count
- Sync Verification API: `VideoPipeline::get_sync_report()` / `isSynchronized()`, `WARN` on violation, 10 s `STAT` summary, per-set `sync.csv`
- Producer–Consumer Pipeline: capture → synchronizer → encoder → storage threads with <span style="color:deepskyblue; font-weight:bold">bounded queues</span> (`mutex` / `condition_variable`) and `std::promise` / `std::future` failure propagation
- Memory Management: per-channel <span style="color:deepskyblue; font-weight:bold">frame pools</span>; queues carry pointers only, so the pool is the hard ceiling on frame memory
- H.264 Encoding & Storage: libavcodec `libx264` encoder (Annex-B `.h264`), only verified sets are encoded, <span style="color:deepskyblue; font-weight:bold">3-minute segments</span> (configurable) managed with `std::filesystem`; every segment starts with SPS + IDR and plays on its own
- Sensor Recording: temperature, humidity and 3-axis acceleration written to the <span style="color:deepskyblue; font-weight:bold">same segment clock</span> as video
- Status Reporting: HTTP `POST /status` via cpp-httplib <span style="color:deepskyblue; font-weight:bold">every 20–30 s</span> (default 25 s, 5 s timeout) with channel, sync, sensor and storage status
- MQTT Control: Eclipse Paho MQTT C (async) on `video/status`, `video/control`, `video/control/ack` and `video/online` <span style="color:deepskyblue; font-weight:bold">(LWT)</span>
- OpenAPI Server: C++ REST server with <span style="color:deepskyblue; font-weight:bold">Swagger UI</span>, status history and control relay to MQTT, shipped as a Docker image
- Monitoring Dashboard: Dear ImGui + GLFW + OpenGL 3; network calls run on <span style="color:deepskyblue; font-weight:bold">dedicated threads</span> so the UI never blocks
- Live Preview: locked sets downscaled to 640x360 JPEG at <span style="color:deepskyblue; font-weight:bold">30 fps</span> on a separate thread, served at `GET /preview` over a kept-alive connection; the dashboard wakes on each new set (about +0.3–0.4 core over a 10 fps preview, recording unaffected)
- Event-Loop Control Plane: components run on a single <span style="color:deepskyblue; font-weight:bold">libuv loop</span> with a message bus and immutable state snapshots
- Graceful Shutdown & Reconnect: the collector keeps recording without broker or server, reconnects with backoff, and finalizes files on Ctrl+C
- Testing: <span style="color:deepskyblue; font-weight:bold">Catch2 (109 test cases)</span>, 4-channel pipeline integration, server API integration, end-to-end and benchmark scripts

## Getting Started

### Prerequisites
- Windows 10/11 with Visual Studio 2022 or later (MSVC x64), or Linux (Ubuntu 24.04 or later)
- Requires CMake 3.16 or later
- Requires C++17
- [FFmpeg](https://ffmpeg.org/) with libx264 (collector only):
  - libavcodec
  - libavformat
  - libavutil
  - libswscale
  - Windows: a pinned FFmpeg 8.1 + libx264 build is downloaded by `scripts/fetch_ffmpeg.ps1` (SHA-256 checked)
- [Mosquitto](https://mosquitto.org/) MQTT broker (or `docker compose up mosquitto`)
- [Python 3](https://www.python.org/) for sample generation, sync verification, E2E tests and benchmarks
- [OpenCV](https://opencv.org/) for the webcam source (optional)
- [libuv](https://github.com/libuv/libuv) 1.51.0 for the event loop (included as third-party)
- [Eclipse Paho MQTT C](https://github.com/eclipse-paho/paho.mqtt.c) 1.3.16 for MQTT (included as third-party)
- [cpp-httplib](https://github.com/yhirose/cpp-httplib) for the HTTP client and server (included as third-party)
- [nlohmann/json](https://github.com/nlohmann/json) for JSON (included as third-party)
- [spdlog](https://github.com/gabime/spdlog) for logging (included as third-party)
- [Dear ImGui](https://github.com/ocornut/imgui) 1.92.5, [GLFW](https://www.glfw.org/) 3.4 and [stb_image](https://github.com/nothings/stb) for the dashboard (included as third-party)
- [Catch2](https://github.com/catchorg/Catch2) 3.11.0 for tests (included as third-party)

## Build Instructions

### Setup and Installation (OpenAPI Server)
```bash
# Build the server only (FFmpeg is not needed)
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DSYNCCAP_BUILD_COLLECTOR=OFF
cmake --build build

# Start the MQTT broker
mosquitto -p 1883

# Run the server (Swagger UI: http://127.0.0.1:8080/docs)
build/synccap_server config/server.json
```

### Setup and Installation (Docker)
```bash
# Mosquitto + OpenAPI server (127.0.0.1:1883, 127.0.0.1:8080)
docker compose up --build

# + collector (synthetic inputs, Linux build, recordings saved to ./recordings)
docker compose --profile full up --build
```

### Setup and Installation (Local, Windows)
```bat
:: Build everything and run ctest (FFmpeg is fetched on the first run)
scripts\build_windows.bat Release

:: Extra CMake options are passed through an environment variable
set SYNCCAP_CMAKE_ARGS=-DSYNCCAP_WITH_OPENCV=ON -DOpenCV_DIR=C:\opencv\build
scripts\build_windows.bat Release
```

### Setup and Installation (Local, Linux)
```bash
# Install dependencies
sudo apt-get update
sudo apt-get install -y build-essential cmake ninja-build pkg-config \
     libavcodec-dev libavformat-dev libswscale-dev libavutil-dev
# Dashboard (GLFW X11 + OpenGL): libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev libgl-dev
# Without the dashboard: -DSYNCCAP_BUILD_DASHBOARD=OFF

# Build the project
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build

# Run the tests (sanitizers: -DPROJECT_SANITIZER=address or thread)
ctest --test-dir build --output-on-failure --timeout 300
```

### Run (Simulation Mode)
```bash
# Generate sample inputs (samples/video/*.mp4|*.avi, needs ffmpeg)
python scripts/make_samples.py

# Broker, server and collector
mosquitto -p 1883
build/synccap_server config/server.json
build/synccap_collector --config config/collector.json                            # 3 file channels + 1 synthetic, CSV sensor
build/synccap_collector --config config/collector.synthetic.json --duration 60    # no input files, stops after 60 s

# Dashboard (server http://127.0.0.1:8080, preview http://127.0.0.1:8090)
build/synccap_dashboard
build/synccap_dashboard --server http://192.168.0.10:8080 --preview http://192.168.0.20:8090 --preview-fps 30

# Verify synchronization of a recorded session
python scripts/verify_sync.py recordings/<session>
```

## API and MQTT

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/status` | Status report from the collector |
| `GET` | `/status` | Latest status + `server_meta` (received_at, stale, collector_online) |
| `GET` | `/status/history?limit=N` | Recent status documents (up to 100) |
| `POST` | `/control` | `{"command":"start"\|"stop"}` → 202 with `request_id`, relayed to MQTT |
| `GET` | `/control/{id}` | `accepted` / `rejected` + reason |
| `GET` | `/health` | Server and broker health |
| `GET` | `/docs` | Swagger UI |

| Topic | Direction | Payload |
| --- | --- | --- |
| `video/status` | collector → | Status JSON (retained, every 5 s) |
| `video/control` | → collector | `{"command":"start"\|"stop","request_id":"..."}` or plain `start` / `stop` |
| `video/control/ack` | collector → | `{"request_id","command","result":"accepted"\|"rejected","reason"}` |
| `video/online` | collector → | `online`, LWT `offline` on abnormal exit (retained) |

│                                    ▼                     └──┬─────────────┬──┘           │

│                          │ preview worker    │              ▼             │ sync.csv     │

│                          └───────────────────┘   │ encoder ch0..chN  │    │              │
│                                                  │ (libx264, per-ch  │    │              │
│                                                  │  queue)           │    │              │
│                                                  └─────────┬─────────┘    │              │
│                                                            ▼              ▼              │
│                                                  ┌──────────────────────────────┐        │
│                                                  │ record queue → storage       │        │
│                                                  │ (.h264, sync.csv, sensor.csv)│        │

│                                                                                          │
└──────────────────────────────────────────────────────────────────────────────────────────┘

Key Components:
1. Loop Thread: runs every control-plane component on one libuv loop; never blocks
2. Blocking Workers: dedicated threads for blocking calls (pipeline start/stop, sensor reads, HTTP reports)
3. Reader Threads: decode each source into a one-picture LatestFrameSlot, so decode jitter never moves the latch
4. Capture Threads: sleep until T - 1.5 ms, spin on steady_clock, latch the latest frame at the common tick T
5. Synchronizer: groups frames per tick, encodes sets within 2 ms and drops (and records) the rest
6. Encoder Threads: one libx264 encoder per channel; a full encoder queue drops the whole set
7. Storage Thread: writes .h264, sync.csv and sensor.csv into time-based segments
8. Preview Worker: downscales locked sets to JPEG off the recording path

Thread Communication:
- Control: Loop Thread → BlockingWorker (submit) → Loop Thread (post result)
- Video Frames: Reader → LatestFrameSlot → Capture → Capture Queue → Synchronizer
- Verified Sets: Synchronizer → Encoder Queues → Encoders → Record Queue → Storage
- Preview: Synchronizer → Preview Mailbox (1, overwrite) → Preview Worker
- Failures: every data-plane thread owns a std::promise; VideoCaptureComponent checks the futures every second
- Thread count for N channels: loop 1 + workers 3 + Paho 2 + data plane 3N + 2 (+ preview 1)

## Known Limitations
- MQTT is plaintext and anonymous (simulation scope); use TLS and accounts in production
- The server keeps status in memory only (latest 100)
- The Linux collector build and the Docker images were not run on the development machine; on Linux only the build without the collector was verified (GCC 13, ASan, TSan)
- A general-purpose OS can preempt the latch; the system cannot prevent it, but always detects, drops and reports it
